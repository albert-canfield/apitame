# GitHub REST API (subset)

A hand-picked subset of the GitHub REST API (repositories, issues, pull requests, search, users and stars), used by the apitame examples. Operation ids, paths and fields follow the official GitHub description.

These tools come from the `github` MCP server, generated by apitame from the OpenAPI spec.
The server runs in **read-only mode**: 13 write operations are blocked.

## Tools

| Tool | Use it to | Operations |
| --- | --- | --- |
| `repos` | Repositories, their content, commits, branches and releases | `repos/get`, `repos/list-for-user`, `repos/list-for-org`, `repos/list-contributors`, `repos/list-languages`, `repos/list-branches`, `repos/list-commits`, `repos/list-releases`, `repos/get-content`, `repos/get-commit`, `repos/get-latest-release` |
| `issues` | Issues, comments and labels | `issues/list-for-repo`, `issues/list-labels-for-repo`, `issues/get`, `issues/list-comments` |
| `pulls` | Pull requests, their files and reviews | `pulls/list`, `pulls/get`, `pulls/list-files`, `pulls/list-reviews` |
| `search` | Search repositories, issues and code | `search/repos`, `search/issues-and-pull-requests`, `search/code` |
| `users` | User profiles | `users/get-authenticated`, `users/get-by-username` |
| `activity` | Stars and stargazers | `activity/list-stargazers-for-repo` |
| `search_operations` | Find any of the 38 operations by keyword | all |
| `call_operation` | Call an operation that has no dedicated tool | any available |

Grouped tools take `{"operation": "<operation id>", "params": {...}}`. Results are JSON: `{"status": <http status>, "data": <body>}`.

Add `"fields"` with dot paths to keep only what you need, for example `"fields": ["id", "name", "items.owner.login"]`. Arrays are handled for you, so `items.name` keeps `name` in every item. It saves a lot of context on large responses.

## Workflows

### List commits, then open one

1. Call `repos` with `{"operation":"repos/list-commits","params":{"owner":"octocat","repo":"hello-world"}}`.
2. Take the identifier (`ref`) of the item the user means from the result, then call `repos` with `{"operation":"repos/get-commit","params":{"owner":"octocat","repo":"hello-world","ref":"main"}}`.
3. Summarize the fields the user asked about instead of pasting the raw JSON.

### List repository issues, then open one

1. Call `issues` with `{"operation":"issues/list-for-repo","params":{"owner":"octocat","repo":"hello-world","state":"open"}}`.
2. Take the identifier (`issue_number`) of the item the user means from the result, then call `issues` with `{"operation":"issues/get","params":{"owner":"octocat","repo":"hello-world","issue_number":1}}`.
3. Summarize the fields the user asked about instead of pasting the raw JSON.

### Search repositories

1. Call `search` with `{"operation":"search/repos","params":{"q":"example"}}`. Find repositories via keywords and qualifiers, for example "mcp language:typescript stars:>100".
2. Useful parameters: `q`, `sort`. Ask the user for missing values instead of guessing.

### Page through long lists

1. List operations such as `repos/list-for-user` accept `per_page`, `page`. Start small, and only fetch the next page if the user needs more.
2. Large responses are cut to fit the response limit; a "note" field says when that happened.

## Safety rules

- Write operations are blocked by the server. Do not look for workarounds. If the user needs one, name the operation and tell them it must be enabled in `apitame.config.yaml` (`mode: read-write` and `writes.allow`).
- Responses over 50 KB are cut. Use filters, pagination and `fields` rather than fetching everything.
- Never ask the user for API keys or tokens: the server already holds them, and they are never shown to you.
- A non-2xx `status` is an API error: read `data` for the reason before retrying.
