# Design decisions

A running log of decisions and the reasons behind them. Newest last. Add an entry when you make a choice that someone would otherwise have to rediscover.

## 001. Safety is the headline, not tool count

**Context.** The landscape review ([landscape.md](landscape.md)) found that search-plus-call tool surfaces already exist in several projects, and that major clients now load tool schemas on demand. Read-only defaults, enforced confirmation and dry runs, together and in a local tool, were not found elsewhere.

**Decision.** Lead with safety: read-only by default, an explicit allowlist, server-enforced confirmation for destructive operations, and dry run on every write. Keep curated tools and token reporting, but present them honestly.

## 002. Node 20.12+ despite Node 20 being end of life

**Context.** Node 20 reached end of life on 30 April 2026. Some current dependency majors (commander 15, vitest 5, better-sqlite3 13) require Node 22.

**Decision.** Support Node 20.12+ for v0.1 because many machines still run it and `npx` users do not choose their Node version. Pin dependency majors that still support 20. CI runs on 20, 22 and 24. Plan to require Node 22 in a later minor release. Superseded by 016.

## 003. MCP TypeScript SDK v2 and the low-level `Server`

**Context.** SDK v2 (`@modelcontextprotocol/server`) is the stable line and implements the 2026-07-28 protocol; v1 is in maintenance. `McpServer.registerTool` expects Zod or Standard Schema inputs.

**Decision.** Use v2 with the low-level `Server` and `setRequestHandler('tools/list' | 'tools/call')`, passing generated JSON Schema unchanged. This keeps tool definitions identical to what `inspect` measures and avoids a lossy JSON Schema to Zod conversion.

## 004. Grouped tools take `{operation, params}`

**Context.** One tool per operation floods the context; a single generic tool hides what the API can do.

**Decision.** Group by tag (or first path segment), list each operation as a one-line signature in the tool description, and validate `params` server-side against the full operation schema. Invalid calls return the full schema, so the agent can correct itself in one round trip. Single-operation tools take their parameters directly.

## 005. SQL: lexer plus parser plus database, not parser alone

**Context.** A SQL parser that differs from the database in how it reads strings or comments can be bypassed. Example: `SELECT '\'; DELETE FROM t; --'` is one statement to `node-sql-parser` and two to PostgreSQL.

**Decision.** Three independent layers: a small lexer that follows each database's quoting rules (statement count, keywords, functions, catalogs), the parser (statement type, INTO, locks, tables), and database enforcement (PostgreSQL `READ ONLY` transaction, extended protocol, cursor, `statement_timeout`; SQLite read-only connection, `query_only`, per-statement read-only check, worker thread for timeouts). Anything the parser cannot read is refused for free-form queries.

## 006. SQLite in a worker thread

**Context.** `better-sqlite3` is synchronous and has no way to interrupt a running statement.

**Decision.** Run SQLite in a worker thread created from inline source (works from both the build and the TypeScript sources). On timeout the worker is terminated and a new one starts on the next call. `better-sqlite3` is an optional dependency so a failed native install never breaks the OpenAPI path.

## 007. Two ways to confirm

**Context.** MCP elicitation lets the server ask the human directly, but not every client supports it.

**Decision.** `confirmation.method: auto` uses elicitation when the client advertises it and falls back to a one-time token bound to the operation and a hash of the exact arguments. The limits of the token flow are documented in [safety.md](safety.md#confirmation).

## 008. Secrets only from the environment, redacted everywhere

**Decision.** The config schema refuses literal secrets. A single `Redactor` is shared by the runtime, auth providers and logger, and is applied to every tool result, error and log line. Errors that may contain secrets are rethrown without `cause`. The ESLint `preserve-caught-error` rule is disabled on those lines with a comment.

## 009. Token estimates without a tokenizer dependency

**Context.** Exact counts need model-specific tokenizers; shipping vocabularies adds megabytes to every `npx` run.

**Decision.** A calibrated heuristic in `src/tokens/estimate.ts`, tuned on real tool lists to land about 15% above OpenAI's o200k encoding, because other tokenizers tend to count more for the same JSON. Always labelled as an estimate.

## 010. Skills are deterministic

**Decision.** Skills are generated from the config and the source with fixed rules, not by a model, so they are reproducible, reviewable and produce clean diffs. They follow the Agent Skills format with the folder name equal to `name`, and are also served through the MCP Skills extension.

## 011. PostgreSQL tests use PGlite over the wire protocol

**Context.** CI and contributors should not need Docker to run the suite.

**Decision.** Integration tests start PGlite (PostgreSQL compiled to WebAssembly) behind `pglite-socket` and connect with the real `pg` driver. The Docker Compose example remains the way to try a full PostgreSQL server. PGlite does not enforce `statement_timeout`, so the driver also sets a client-side `query_timeout`, and pool connections carry a permanent error listener so a protocol hiccup can never crash the server.

## 012. Config files written by `add-to` are portable

**Decision.** When the config is inside the project, client configs reference it through the client's project variable (`${CLAUDE_PROJECT_DIR:-.}` for Claude Code, `${workspaceFolder}` for Cursor and VS Code) so they can be committed. Codex gets an absolute path because its config does not document interpolation. The launcher pins the minor version (for example `apitame@0.3`).

## 013. Releases use npm trusted publishing

**Context.** npm requires two-factor authentication to publish and is restricting tokens that bypass it. v0.1.0 was published manually with a short-lived token.

**Decision.** Releases run from `.github/workflows/release.yml` on a version tag, with npm trusted publishing (OIDC from GitHub Actions, npm 11.5.1 or later) and provenance. No long-lived npm token is stored: trusted publishing was configured on npmjs.com on 15 October 2026 (this repository, `release.yml`, environment `npm`, publish only), after v0.1.0 to v0.3.0 had been published with a granular token, and that token's repository secret was deleted. The workflow still reads an `NPM_TOKEN` secret if one is ever added back, as an emergency fallback. The workflow skips publishing when the version is already on npm and skips the GitHub release when it already exists, so a release can be finished by hand without breaking the workflow.

## 014. Bundle only the SQL parsers apitame needs

**Context.** `node-sql-parser` installs about 88 MB (every dialect plus source maps), while apitame uses three dialect builds of about 800 KB. It was most of what every `npx apitame` user downloaded, even for OpenAPI-only use.

**Decision.** Import the PostgreSQL, MySQL and SQLite builds statically and let the bundler include them (with `big-integer`), keep `node-sql-parser` as a development dependency, and load all SQL code lazily so OpenAPI users never parse it. Published builds have no source maps. License texts are shipped in `THIRD_PARTY_NOTICES.md`. Install size went from about 141 MB to 53 MB.

## 015. HTTP sessions are opt-in

**Context.** Elicitation lets the human approve a destructive call in the client, but the server must send a request in the middle of a tool call and receive the answer. Stateless HTTP builds a fresh server per request, which never sees `initialize` (so it does not know the client can elicit) and cannot receive the reply.

**Decision.** `serve --transport http --sessions` keeps one server per client, keyed by `Mcp-Session-Id`, with an idle timeout (30 minutes, counted only while no request or stream is open) and a cap (100, the oldest idle session makes room). Stateless stays the default: it is simpler to run behind load balancers and has no per-client memory. All sessions read the same live runtime, so `--watch` reloads and confirmation tokens work the same way in both modes.

## 016. Require Node 22 or later

**Context.** Node 20 reached end of life on 30 April 2026 (see 002). Supporting it held back dependency majors (commander 15, better-sqlite3 13, vitest 5) and cost workarounds: on Node 20 a timeout signal reachable only through `AbortSignal.any()` can be garbage collected and never fire, which hid a real bug until 0.2.0.

**Decision.** From 0.3.0, require Node.js 22 or later (`engines.node: ">=22.0.0"`). CI drops Node 20, `doctor` fails on older versions, and Dependabot no longer holds back majors that need Node 22. Contributed by @Enard52 in #48.

## 017. Node 22.14 is the floor, TypeScript 7 waits

**Context.** After 016, TypeScript 7 is the native compiler and has no JavaScript compiler API: `tsc --noEmit` passes, but typescript-eslint refuses to load ("typescript-eslint does not support TS 7.0") and the tsup declaration build fails (`Cannot read properties of undefined (reading 'useCaseSensitiveFileNames')`). better-sqlite3 13 ships prebuilt Node-API 10 binaries while declaring `node: ">=22"`: on Node 22.0 to 22.13 opening a database crashes the process with a segmentation fault, so `apitame init` and `test` on a SQLite file exit with code 139 and no message. CI runs the latest Node 22 and cannot see this. commander 15 declares Node 22.12+.

**Decision.** Require Node.js 22.14 or later (released February 2025), which makes better-sqlite3 13 and commander 15 safe, and check it in `doctor`. Stay on TypeScript 5.9 and have Dependabot ignore its majors until typescript-eslint and tsup support 7. `@types/node` follows the minimum supported Node (22), so code cannot use APIs that Node 22 lacks.

## 018. HTTP auth through an external OAuth authorization server

**Context.** Over HTTP, apitame's only authentication was one static token (`APITAME_HTTP_TOKEN`) shared by every client. That is fine on one machine, but a team that shares one server cannot tell users apart, cut one person off without handing everyone a new token, or rely on its identity provider's sign-in and policies. The MCP authorization spec expects an MCP server to act as an OAuth 2.1 resource server, and MCP clients already know how to sign users in once a server points them to an authorization server.

**Decision.** apitame is a resource server only. With `http.oauth`, it publishes RFC 9728 protected resource metadata naming the configured issuer, answers requests without a valid token with a 401 that points to that document, and accepts JWT access tokens (RFC 9068) that it checks locally: signature against the issuer's JWKS (found through RFC 8414 or OpenID Connect discovery), `iss`, `aud`, `exp` and required scopes. Running an authorization server (login pages, client registration, consent, token storage) is a product of its own and better left to Keycloak, Auth0, Okta, Entra ID and the like. Verification uses `node:crypto` rather than a JWT library: with an allowlist of asymmetric algorithms and a check that each key is only used with the algorithm it was published for, it takes a few hundred lines and adds no dependency, and the bearer parsing and challenges come from the MCP SDK. Because tokens are checked locally, cutting someone off at the authorization server takes effect when their access token expires (streams are closed then too), so short token lifetimes matter. The static token stays for single-user setups and cannot be combined with OAuth. Opaque tokens (token introspection, RFC 7662) were left for later; see 024.

## 019. Approvals through multi round-trip input (protocol 2026-07-28)

**Context.** MCP protocol 2026-07-28 removed requests from server to client. A server that needs input answers the call with an input-required result, and the client retries with the answers (multi round-trip input). Every request also carries the client's capabilities, so a stateless server knows whether the client can show a form. apitame asked for approval with `elicitInput()` in the middle of a tool call, which 2026-07-28 clients cannot receive, and which over HTTP needed `--sessions`. The SDK (`@modelcontextprotocol/server` 2.3) only negotiates 2026-07-28 through its era-aware entries (`serveStdio`, `createMcpHandler`), not on a server connected to a transport by hand.

**Decision.** Serve both eras. stdio goes through `serveStdio` with a server factory. HTTP keeps every existing check (Host, Origin, static token, OAuth) in front, reads the body once, and routes with the SDK's `isLegacyRequest`: 2025-era requests to the existing stateless or session wiring, unchanged, and 2026-07-28 requests to a strict `createMcpHandler`. 2026-07-28 requests are stateless by design, with or without `--sessions`. 2025-era connections keep `elicitInput()`; the SDK's shim that could serve input-required results to them is turned off, because its failures skip the audit log and its timeout is 10 minutes.

On a 2026-07-28 request whose capabilities include form elicitation, the first call stores a random approval id (256 bits) and returns the same form as before, with the id as `requestState`. The id is one-time, expires after `confirmation.ttlSeconds`, and is bound to the operation, a hash of the exact arguments and the OAuth client and subject, so one user cannot spend another's approval. It lives in its own map next to the confirm tokens, so neither works as the other. The second call runs only if the id checks out and the box came back checked. A wrong or forged answer, changed arguments, another user, an expired or reused id and a decline are refused with nothing sent and use the id up; a second round that stops earlier (a dry run, invalid arguments, a blocked operation, the write rate limit) sends nothing and leaves the id usable once until it expires. Without form elicitation, `auto` falls back to the token flow and `elicitation` refuses, as for 2025-era clients. The write rate limit is checked before asking, without reserving a slot. The audit log keeps `confirmation-requested`, `declined` and `sent`, and records a refused approval id as `approval-refused` with the reason (`unknown`, `used`, `expired`, `mismatch`), so a forged or replayed id is never mistaken for a human decline.

Elicitation proves that the MCP client answered, not that a human did. That holds only when the agent cannot reach the server itself: over stdio, or over HTTP with a token or OAuth client the agent does not hold, on a port its sandbox cannot reach. Over HTTP without authentication, any local process can answer the form with two plain requests, so `serve` warns at startup when it runs that way and some operation asks for confirmation, and `confirmation.method: elicitation` refuses approvals there, in both protocol eras, before anyone is asked. That keeps the setting's meaning: an approval under `elicitation` must come from the client the human uses, and a 2025-era session opened by a local script is no better proof than two 2026-07-28 requests. This is a breaking change for 2025-era clients that used `--sessions` without authentication under `elicitation`; they now need a token, OAuth or stdio.

The id is not signed (`createRequestStateCodec` would need a key): it is only a lookup key into memory, which is enough in one process. Approvals in flight therefore live in the process that asked, like confirm tokens; several processes behind a load balancer need sticky routing, and a restart or reload forgets them. Over HTTP, `serve --watch` publishes list changes to an event bus that serves 2026-07-28 clients' `subscriptions/listen` streams, which are limited like sessions (100 in all, and 10 per OAuth user); over stdio the connection's server delivers them on those streams. `--log-level debug` logs the era of each stdio connection and HTTP request, so users can tell which protocol their client speaks.

## 020. DuckDB: an optional peer dependency, DuckDB's own parser and a child process

**Context.** `@duckdb/node-api` ships one native binary per platform, 38 MB (win32-x64) to 117 MB (darwin-arm64) unpacked, against about 53 MB for all of apitame. node-sql-parser has no DuckDB dialect, and its PostgreSQL build refuses common DuckDB syntax (`EXCLUDE`, `GROUP BY ALL`, `QUALIFY`, FROM-first queries). DuckDB also runs some dangerous functions on a read-only, locked database: `query()` and `query_table()` run SQL strings, `enable_logging(storage = 'stdout')` prints every later query to standard output (the MCP channel over stdio), and `enable_peg_parser()` switches the parser for every connection of the instance. An adversarial review of the first version found that DuckDB runs in the server's own process were the weak point: one query (`list_transform(range(25000000), ...)`) ran Node out of memory while its result was converted, `interrupt()` does not stop DuckDB while it plans a query or folds constants (a 600-way self-join ran past two minutes at a 500 ms timeout), each call could use 80% of the machine's memory, every core and spill to 90% of the free disk next to the database, DuckDB copied a proxy URL with its password from the environment into a setting that queries could read, and the catalog functions showed every table's DDL and file paths past the table lists.

**Decision.** The driver is an optional peer dependency, found with `import.meta.resolve` but never loaded by the server itself, and a development dependency for tests. A missing driver gives an error with the exact `npx -p apitame -p @duckdb/node-api@1.5.6-r.1 apitame ...` command, and `add-to` pins the same tested release in client configs, so every start runs the DuckDB the tests ran. Every DuckDB release is a semver prerelease (`1.5.6-r.1`), which no range such as `>=1.4.0-r.1 <2` matches outside its own patch version, and npm then fails `npx -p apitame -p @duckdb/node-api` with ERESOLVE (tested). Only `*` is accepted for every release, so the peer range is `*`; apitame refuses DuckDB older than 1.4 and warns when the driver is newer than the tested minor release. Moving to a newer release means updating the development dependency and `DUCKDB_TESTED_VERSION` together and running the tests.

All DuckDB work runs in a child process (`dist/duckdb-worker.js`, forked with a 512 MB V8 heap and an empty environment, its output discarded), one call at a time. The parent arms the call's deadline before sending it and kills the child when the deadline passes, so the timeout covers planning too; a crash or an out-of-memory end of the child is an error for that call only, and a new child starts on the next one. Inside the child each call opens the file in its own read-only instance (a few milliseconds) with external access off, `memory_limit` and `threads` from `sql.duckdb` (1GB and 2), no spilling to disk, an explicit `http_proxy` placeholder and a locked configuration, all read back before anything runs; nothing a query changes in the engine outlives the call, other programs can write to the file between calls, and every call sees the latest data. Results are cut at the row limit or the response byte budget, and the sizes of lists, maps and structs are checked before they are read, so a single huge value is refused instead of built. A worker thread would have been lighter, but it shares the process's memory and cannot stop a native call that ignores interruption; only a process can be killed safely.

The parser layer is DuckDB's own: `json_serialize_sql(?)` on a separate in-memory database in the child, with the query bound as a parameter, so it is parsed but never run there. It must return exactly one SELECT; apitame walks the tree for tables (CTE names resolved per scope as DuckDB binds them, checked against DuckDB), function calls and table functions, and refuses tree shapes it does not know. This parser cannot disagree with the engine, which is what bit the other engines, but it is not independent of it: the lexer and the database settings are the layers that do not share its code. Table functions in FROM must be on a short reviewed list of row generators rather than merely not denied, so a new DuckDB release cannot add a reader or a state changer that gets through. The catalog (`duckdb_*` and `pragma_*` functions and views, `information_schema`, `pg_catalog`, `sqlite_master`, `SHOW`, `DESCRIBE`) and setting readers (`current_setting`, `getvariable`) are refused, because they show structure, settings and paths past the table lists; `list_tables` and `describe_table` cover structure and apply the lists. External access off does not stop DuckDB from reading the database file itself (`read_blob('data.duckdb')` returns raw pages) or attaching it again, so the name lists in the lexer and the parser are what refuse those, and the tests check both. Named write queries are left out: DuckDB allows one writer or many readers per file, and the read-only path covers the requests so far.

## 021. Argument rules for writes

**Context.** A write was either allowed (`writes.allow`) or not. Nothing limited how an allowed operation was called: with `createRefund` allowed, an agent could refund any amount on any charge, and confirmation only helps when a human reads every preview carefully (#58).

**Decision.** `writes.rules` maps an exact operation id (or named query) to argument paths and constraints: `in`, `notIn`, `equals`, `pattern`, `min`, `max`, `minLength`, `maxLength`, `required` and `forbidden`, plus `optional`. The choices behind it:

- **Exact ids, not patterns.** `writes.allow` takes `*` because it grants; a rule restricts, and a pattern that stops matching after a spec update would drop a restriction silently. `serve`, `inspect` and `doctor` warn about ids and fields that do not exist, and rules on reads, which are ignored.
- **Paths are tool arguments**, as the agent sends them: `body.state`, and `[]` for every item of a list (`body.items[].price`). `[]` rather than `*`, because `*` already means a pattern in `writes.allow`, and `*` in a path is refused so that `items.*.price` cannot quietly match nothing. Indexes are not supported: a rule on one item is rarely what anyone means.
- **Where they run.** After argument validation, so rules see coerced values (`"5000"` for an integer is 5000), and before dry runs, confirmation, the write rate limit and the request. A refused call never reaches a human, never uses up the write budget and is recorded as `blocked` with the rule as the reason. Rules sit after the allowlist decision, so they can only narrow it.
- **Missing values fail closed.** A value rule (`in`, `notIn`, `equals`, `pattern`, `min`, `max`, `minLength`, `maxLength`) refuses a call that leaves its value out, unless the rule says `optional: true`, in which case it checks the value only when it is there. JSON Schema does the opposite (constraints skip missing properties), and the first version of this feature followed it, with `required: true` to make a value mandatory. But for a write, absent often means "everything" or "the default": `amount: { max: 5000 }` let a refund without an amount through, which on many APIs refunds the whole charge. A rule that can be dodged by leaving the argument out protects nothing, so the safe reading is the default and the exception is spelled out per path. `required: true` stays valid, and is redundant next to value operators. For a path through a list, a missing list (or an item without the field) is missing, and an empty list passes, since it has no item to break the rule. `null` is a value: every value operator refuses it unless `in` or `equals` lists it (`notIn` included, since an API may read `null` as the default), it is missing for `required` and set for `forbidden`.
- **Fail closed on doubt.** A value whose shape does not fit the path (`items` sent as an object) is refused rather than skipped. `notIn`, a denylist, matches loosely (case, surrounding spaces, numbers by value) while `in` and `equals` match strictly (only the usual text form of a number or boolean, `"42"` for 42), so a near miss refuses in both cases.
- **Patterns run on our own matcher.** JavaScript's regular expressions backtrack: with a rule like `^(a+)+$` or even `^\d+\d+$`, a crafted value can take minutes, and an agent controls the value. A heuristic for "dangerous" patterns misses polynomial cases, and RE2 is a native dependency. `src/safety/pattern.ts` parses the common subset (classes, groups, alternation, counted repetition, anchors), compiles it to a small automaton and runs it as a Pike VM in time linear in the value, in about 400 lines with no dependency. Backreferences, lookaround and `\b` are refused when the config loads, patterns are capped at 200 characters and the compiled program at 2,000 instructions. A seeded differential test checks it against `RegExp` on thousands of random patterns.
- **The agent learns the rules up front**: tool descriptions, `search_operations` results and the generated skill list them in plain language, skill examples are adjusted to follow them, and a refusal lists every broken rule so one retry can fix them all.
- **`writes` is now a strict object**, like the top level and `http`, because a typo such as `rule:` would otherwise leave every write unrestricted without a word.

## 022. Per-user permissions and rate limits with OAuth

**Context.** With `http.oauth` (018), every user with a valid token got the same tools, the same write allowlist and shared rate limits; scopes only decided who could connect. A team that shares one server needs different access per person or per client without running one server per access level, and one user's looping agent should not use up everyone's budget.

**Decision.** `http.oauth.permissions` has a `default` entry that every OAuth caller gets, and maps token scopes (`byScope`) and client ids (`byClient`) to entries that add to it. Each entry has `mode`, `writes` and `tools`. Two keyed maps instead of scope names directly under `permissions`, so a scope and a client of the same name cannot collide and a scope written at the wrong level is an error with a hint.

- `default` is the baseline, read-only with every tool when it is not set, and matching entries only add to it. A first version gave `default` only to callers that no entry matched, so a token without a narrow scope (a contractor's `mode: read-only`, say) got the wider `default`: fewer scopes, more access. With a baseline a token never gains anything by leaving a scope out. The price is that an entry cannot restrict: `default` must be the least any caller gets, and an entry that adds nothing to it is reported.
- Entries add one by one, not field by field. A tool is shown if one entry shows it, but a write runs only if one single entry grants it in `writes` and reaches the operation through its own `tools`. The first version merged all writes and all tools separately, so an entry showing every tool without writes and an entry granting every write in one tool combined into writes in every tool, which neither granted. An entry's `writes` that its own tools cannot reach are reported. Union, also between scope and client entries, keeps one rule (entries grant) and matches how authorization servers combine scopes; a client is restricted at the authorization server, through the scopes it may receive.
- `call_operation` reaches the operations in no group, and those of the groups the caller sees: hiding a group hides its operations from `call_operation` and `search_operations` too, so `tools` limits reads. A group keeps the shape the server config gives it (`operation` and `params`) for every caller, even with one operation left.
- Permissions only narrow the server config. A write must match both `writes.allow` and an entry's patterns (two pattern lists cannot be merged into one, so both are checked for each id), and a read-only server stays read-only. Adding permissions can never open what the server config keeps closed, and `mode` and `writes.allow` stay the switches that close things for everyone.
- Enforcement is one more step in `decide()`, after `mode` and `writes.allow`, through an optional `caller` in the policy. Both runtimes pass the caller's permissions wherever they called `decide()` before, so tool lists, grouped tools, `search_operations`, `call_operation`, SQL named queries and confirmations agree, and a refused write is never sent and never asks the human. Permissions are decided before argument rules (021), so a caller that may not use an operation is refused as not permitted, never with a rule message, and rules still apply to every caller that may. The OpenAPI runtime builds the tool list for each permission set (a group lists only the caller's operations, `call_operation` describes what the caller can run) and keeps the last 32. `tools/list` reads the caller from `ctx.http.authInfo` like `tools/call`, so stateless requests, sessions and 2026-07-28 requests are all answered per caller. A hidden tool answers exactly like one that does not exist, SQL named queries included (the check runs before argument validation), and an unknown tool name is refused before anything else looks at it. Refusals name only the caller's own matching entries. Server instructions and skills still describe the server config; per-caller versions are left for later.
- `*` patterns are matched without regular expressions. Tool names and operation ids can come from clients, and the regular expression the matcher used to build backtracked: a tool name of a few hundred kilobytes ending in a newline blocked the server for seconds. A two-pointer matcher takes time linear in the name.
- The MCP layer passes the token's scopes next to the caller. The audit log records the entries that applied (`permissions`), not the raw scopes, and approvals stay bound to client and subject.
- Without an OAuth caller (stdio, `APITAME_HTTP_TOKEN`, HTTP without authentication) nothing changes.
- A name in `tools` or `writes` that matches nothing, a write pattern that grants nothing (outside `writes.allow`, or out of reach of its entry's tools) and an entry that adds nothing to `default` are warnings, checked when the runtime is built because OpenAPI operation ids come from the spec. They can only fail to grant, never widen access. An error would stop `serve` when a spec loaded from a URL drops an operation that an entry names, and would make a `--watch` reload that takes a tool or an operation away keep the old config instead. `serve` logs them at startup and on reload, `doctor` reports them under Config and `inspect` lists them, as for `writes.rules`. Mistakes in the shape of the config (wrong types, `mode: read-only` with `writes`, scope names directly under `permissions`) stay errors.
- The runtime applies the permissions and `--watch` rebuilds it, so they change on reload without a restart, and a change to them counts as a tool list change. The rest of `http.oauth` needs a restart, because the transport checks tokens with the settings it started with: a reload that removes or changes it is refused while apitame checks OAuth tokens, since a runtime without `http.oauth` would serve those callers with no permissions at all. A call already waiting for a human approval on a 2025-era connection finishes on the runtime it started on.

`limits.perCaller` adds calls and writes per minute for each OAuth caller, keyed by client and subject apart, as sessions are. A call is checked against the caller's own budget first, so a refused call does not use up the shared budget. It is off by default (`0`): good numbers depend on the team and on the server-wide budget, which apitame cannot guess. Idle callers are forgotten once 1,000 are tracked.

apitame still advertises only the required `scopes` (in the 401 challenge and the metadata), and MCP clients request those. A permission scope therefore reaches a token only when the authorization server adds it or the client asks for it. Advertising every `byScope` key would make clients ask for all of them, which some authorization servers grant to anyone who asks and others answer by refusing the sign-in. `byClient` works without any of this. Matching other claims (roles, groups) and rate limits per entry are left for later.

## 023. `apitame diff`: two versions of the spec, one config

**Context.** The config is meant to be reviewed in a pull request, but a new version of the spec changes what the agent can do without touching it: a new `deleteAll` operation that `delete*` allows, a GET that became a POST, an operation renamed so that its rules no longer apply. Nothing showed a reviewer what changed for the agent (#60).

**Decision.** `apitame diff <old-spec> [new-spec]` builds both versions into a runtime with the same config, exactly as `serve` and `inspect` build them, and compares the results: operations, access levels, what the allowlist lets through, config references, the arguments of allowed writes, the base URL and the token cost of the tool list. It only reads the specs. Credentials, `source.baseUrl`, static headers, rate limits and the audit log are left out of the comparison, so it needs no environment variables, sends nothing and writes nothing. The choices behind it:

- **One config for both sides, the current one.** The question is what this config does with the new spec. A pull request that changes both is compared under its new config, so a wildcard added to `writes.allow` in the same pull request is caught. A change to the config alone shows up in the pull request's own diff, which reviewers read already.
- **An exact id is a review, a pattern is not.** A new write is one the agent can call in the new spec, could not call as a write before, and that no one named: allowed by a `writes.allow` pattern, or a POST, PUT, PATCH or DELETE that runs as a read through a `writes.treatAsRead` pattern or `x-apitame-access: read` in the spec. The last two run even in read-only mode, so `mode` does not make them safe. Listing an id by name is taken as the decision to allow it.
- **A renamed operation is new to the config.** Rules, `confirm`, `destructive` and groups name exact ids, and they stay with the old id. `createRefund` renamed to `createOrderRefund` and allowed by `create*` loses its amount limit and its approval, and `serve` only warns that a rule names an unknown id. Renamed writes are therefore new writes, even under `*`, and the references they leave behind are listed with the new id so the fix is one rename in the config.
- **Renames are found by a heuristic, and only when it is unambiguous**: a new id on the same method and path (path parameter names aside) when exactly one operation on each side has them, or the same id on a new method or path. Anything else is an addition and a removal, which is the safer reading: an addition is checked against the allowlist from scratch.
- **Access changes count in both directions.** A downgrade can matter more than an upgrade: a destructive operation that becomes a write stops asking for approval, and a write that becomes a read runs in read-only mode, outside the allowlist and its rules.
- **`--fail-on` takes categories**, one per section of the report, separated by commas, with `new-writes` when it is given without a value and `any` for all of them. Without it, diff is a report and exits with code 0. A listed category with findings exits with code 1, and so does a spec that cannot be read, so a CI check fails closed. The token cost is reported but is not a category: `inspect --max-tokens` already sets a budget, and a delta has no threshold that fits every API.

## 024. Token introspection for opaque access tokens

**Context.** `http.oauth` (018) only accepted JWT access tokens, checked locally. Some authorization servers issue opaque tokens that only they can read, and with local checks a revoked token stays valid until it expires (#62). RFC 7662 lets a resource server ask the authorization server about a token. That puts a network call in the request path, and every made-up token sent to apitame would become a request to the authorization server.

**Decision.** `http.oauth.introspection` (`url`, `clientId`, `clientSecret`, `clientAuthMethod`, `cacheSeconds`, `maxCallsPerMinute`) and `http.oauth.verify` choose how tokens are checked:

- **`verify: jwt | introspection | auto`.** `jwt` is today's behavior. `introspection` asks about every token, JWTs included, which also makes revocation take effect quickly. `auto` checks tokens shaped like a JWT (three parts, the first a JSON header) locally and introspects the rest, for servers that issue both; a JWT-shaped token never falls back to introspection, so a forged one costs no request and the two paths cannot be played against each other. The default follows the config: `introspection` when `introspection` is set (the block alone, as in the issue, does what it says), `jwt` otherwise. Combinations that cannot work are config errors rather than silently ignored settings: `introspection` or `auto` without the block, `jwt` with it, and `jwksUri` or `requireAccessTokenType` when no JWT is checked locally. The key is `verify` rather than `mode`, because `mode` already means read-only or read-write at the top level and in every permission entry right below it. `clientAuthMethod` matches the key of the same name under `auth` (OAuth2 client credentials).
- **Same checks as JWTs.** After the signature check, the JWT verifier's claim checks moved into one function that both verifiers call: `aud` against `resource` and `audiences`, a required finite `exp`, `nbf` and `iat` with a minute of skew, ID and refresh token markers, scopes, client and subject, `clients`. Only `iss` differs: RFC 7662 makes it optional in an answer that comes from the authorization server itself over an authenticated request, so it is checked when present. `active` must be exactly `true`. A token without `exp` is refused rather than capped to the cache time: the JWT path refuses it, the MCP SDK's bearer check requires an expiry, the transport closes streams when it passes, and a credential that never expires is not what an access token should be. On top, `token_type`, `token_use` and `typ` must not name a refresh, offline or ID token. A review found that markers compared as written let `Refresh Token` or ` refresh_token` through, so names are compared without case, spaces, dashes, underscores or a URN prefix, and anything with `refresh` in it is refused; this applies to the `typ` of JWTs too, where it can only refuse more. Markers are a second line, though: the audience check is the defense that counts, since an authorization server may report any token it issued as active. Tokens bound to a client key or certificate (`token_type: DPoP`, or a `cnf` member, RFC 9449 and 8705) are refused: apitame cannot check the proof, and accepting them as plain bearer tokens would undo the binding. The JWT path does not refuse `cnf` yet; changing it would change behavior for existing setups, so it is left for a separate decision.
- **One description for every refusal.** A review showed that distinct 401 descriptions (not active, wrong audience, expired, client not listed) let anyone with a token learn what the authorization server knows about it, which RFC 7662 section 4 warns about. Every refusal of an introspected token says `The access token is invalid or inactive.`; the reason travels as the error's `cause`, which the transport writes to the debug log. JWT refusals keep their reasons: whoever holds a JWT can read its claims anyway. Answers without `sub` make all users of a client one caller (sessions, `limits.perCaller`, audit), so apitame warns once per client (at most 1,000 clients) and does not use `username`, which RFC 7662 describes as a name for people.
- **Fail closed, but as a server error.** A network error, a timeout (5 seconds), a redirect (never followed), a status other than 200, an answer over 1 MB or one without a boolean `active` refuses the token. The verifier throws a plain error, which the transport logs and the SDK answers with a 500 that hides the details. A 401 would tell the client its token is bad, and MCP clients answer that by signing the user in again, which does not help when the authorization server is down. The error page of a failed request is never read, since it may echo the credentials; it is cancelled, which closes the connection, and so is a body whose `Content-Length` is over the cap. The timeout covers the whole answer, with a deadline held by a timer (`withDeadline`): a review found that an `AbortSignal.timeout` signal could be collected after the headers arrived, so a server dripping its body held the request, and every later request for that token, forever. Before any request, what is not an RFC 6750 bearer token or is over 16 KB is refused locally.
- **Cache.** Only active answers are cached, for `min(cacheSeconds, exp - now)`, with `cacheSeconds` 60 by default and at most 300, so a revocation takes effect within five minutes at worst. Without a negative cache, junk tokens cannot fill memory or push out good answers. Keys are the SHA-256 of the token, and the cached value is the verified result without the token, so the process holds no raw token outside the request in flight; a test inspects the whole verifier to check that. The cache is a least recently used map of at most 10,000 tokens, and each request gets its own copy of a cached answer. Concurrent requests with the same new token share one introspection.
- **Two budgets against amplification.** At most `maxCallsPerMinute` introspections (600 by default) of new tokens start in any 60 seconds, the same idea as the key set refresh limit of 018. Past it a new token is refused with a 500 and a warning is logged at most once a minute. A first version had one budget for everything and claimed that cached tokens kept working, but a cached answer lives only `cacheSeconds`: from the second minute of a flood at the cap rate, every signed-in user's re-check competed with junk for the same slots, and everyone got 500s. Serving stale answers instead would have weakened revocation. So tokens the server has said were active are remembered (by hash, until their `exp`, in the same bounded map) and checked again within a second budget of the same size. Made-up tokens cannot reach it, because only the authorization server can make a token active; real users are bounded by `cacheSeconds` (one re-check per active token per period), and the budget is capped all the same. A refused token is forgotten, so a revoked one counts as new afterwards. In all the authorization server sees at most twice `maxCallsPerMinute` a minute. A per-address budget for new tokens would be fairer still, but apitame cannot tell callers apart before their token is checked, and an address is often a proxy's.
- **Credentials.** `clientSecret` must be `${VAR}` references only: no default (`${X:-hunter2}` is a secret in the config) and no text around them. It is resolved when `serve` builds the verifier (so stdio never needs it), registered with the redactor together with the Basic credentials made from it, and never logged. `clientId` may be literal and is not treated as a secret, as under `auth`. `url` is not resolved, so `${` in it is refused rather than sent as written. `doctor` reports missing variables. With Node's proxy support (`NODE_USE_ENV_PROXY=1`), requests go through the configured proxy, credentials included, even to loopback; the docs say to use `https` or `NO_PROXY`. At startup, before listening, apitame introspects a random token that nobody issued, which checks the URL and the credentials. A failure to reach the endpoint is logged and apitame keeps serving, as when the key set cannot load; an endpoint that calls that token active would accept anything, so apitame stops. That check counts against the budget for new tokens.

The URL is configured, not discovered from the issuer's metadata: discovery would add a document whose answer decides where apitame sends tokens and its client secret. Authorization servers without RFC 7662 (Google, GitHub) are still not supported: they have token check APIs of their own, each with its own request and answer format, and supporting them would mean a verifier per provider. An open stream is not checked again while it stays open, so a stream opened with a token that is then revoked lasts until the token expires, as with JWTs; requests on it are checked as usual.

## 025. A container image built from the npm package, and HTTP checks in `doctor`

**Context.** With OAuth (018) and per-user permissions (022), apitame became a server a team can share, but running one meant writing a Dockerfile, choosing a reverse proxy, and getting `http.oauth.resource`, the proxy's routes and the identity provider's metadata to agree. A mistake there shows up as a client that cannot sign in, with little to go on (#61).

**Decision.** An official image, `ghcr.io/albert-canfield/apitame`, a deployment guide (`docs/deploy.md`) and HTTP checks in `doctor`.

- **The image installs the npm package.** The Dockerfile packs the checkout with `npm pack`, as `npm publish` packs it, and installs that tarball with `npm install -g --omit=dev --ignore-scripts`. The image therefore runs the files npm ships, with the dependency versions an install resolves that day (the package has no lockfile, and the scan checks what was resolved). Installing `apitame@<version>` from the registry would prove that the image holds the published artifact, but npm makes a new version visible asynchronously, so the job would have to poll, and pull requests and dry runs could not build an unreleased version the same way. Building from the tagged commit, in the same workflow and after the publish job, ties both to one commit, and the attestation records it.
- **Debian 13 slim and the Node.js binary, nothing else from the Node image.** The runtime stage copies `node` from the official `node:22` image onto plain Debian, so npm, npx, yarn and corepack are left out: 31 MB less, and their bundled dependencies are not there to scan or patch. glibc, because better-sqlite3 ships prebuilt glibc binaries (only the target platform's is kept). Distroless has no `/usr/bin/env`, so the CLI's shebang and `ENTRYPOINT ["apitame"]` would not work, and a shell helps whoever debugs a deployment. Both base images are pinned by digest in their `FROM` lines, where Dependabot updates them (not Node majors).
- **No DuckDB driver.** It would add about 90 MB (22 MB compressed) for a source that HTTP deployments rarely use; in the npm package it is an optional peer for the same reason. `docs/deploy.md` shows a two-stage Dockerfile that adds the tested release.
- **Authentication stays mandatory.** In the image apitame listens on `0.0.0.0`, which `serve` already refuses without `APITAME_HTTP_TOKEN` or `http.oauth`. No opt-out was added: publishing the port on the host's loopback does not make the container's interface a loopback one, and an image that started without authentication would make that the most common deployment.
- **A fixed, numeric, non-root user (10001)**, so Kubernetes can verify `runAsNonRoot` and the UID does not match the first user of a Linux host. `/audit` is owned by it, as the one place apitame writes (`audit.file`), and a named volume mounted there inherits that owner. The image works with `--read-only` and a tmpfs on `/tmp`.
- **`/health` keeps its answer.** It existed (`{"ok":true}`) and keeps that body, so nothing that already polls it breaks. It now answers GET and HEAD only, with `Cache-Control: no-store`, and on loopback goes through the Host check: otherwise a web page could use DNS rebinding to read it and learn that apitame runs on the machine. The Origin check would not help there, since browsers send no Origin on a same-origin GET. Beyond loopback nothing is checked before authentication anyway, and probes send any Host. The image's health check calls it with `node -e`, since the image has no curl.
- **Release.** A separate `image` job runs after the npm `publish` job, with only `contents: read`, `packages: write`, `id-token: write` and `attestations: write`. Before anything is pushed it builds linux/amd64, runs the smoke test and scans the image with Trivy, failing on a critical vulnerability that has a fix (arm64 holds the same packages). Then it builds linux/amd64 and linux/arm64 with provenance (`mode=max`) and an SBOM, pushes `<version>`, `<major>.<minor>` and `latest` (not for pre-releases) only on version tags, and pushes a signed build attestation to the registry. If it fails after npm published, it can be re-run alone. The manual dry run builds and scans without pushing. Third-party actions are pinned by commit SHA, and Trivy's own version too: trivy-action was hit by a supply chain attack in March 2026 and moved its tags to a `v` prefix afterwards; the pinned v0.36.0 came later. CI builds the image on every pull request and runs the same smoke test, never pushing; the test suite never needs Docker.
- **`doctor` checks HTTP deployments** when the config has `http.oauth`, when `APITAME_HTTP_TOKEN` is set, or with `--http` or `--host`. `--host` exists because where `serve` listens is a command line flag that `doctor` cannot see, and whether authentication is required depends on it. The checks live in their own module, one function per check in a list, with a shared context so that a later check can read what an earlier one found (a token introspection check, for one, would read the issuer's metadata). The signing keys are loaded by `JwtVerifier.warmUp()`, exactly as `serve` loads them, and the metadata is fetched with the same limits (no redirects, 10 seconds, 1 MB). The public URL check asks the resource, through the proxy, for apitame's 401 challenge and the metadata it points to, because the likeliest proxy mistake is a route for `/mcp` without one for `/.well-known/oauth-protected-resource`. An unreachable public URL is only a note: `doctor` often runs before the deployment does. With `http.oauth.introspection`, `doctor` builds the introspection verifier with `serve`'s own code (`createOAuthVerifiers`, which resolves and registers the secret and checks the URL) and calls its `warmUp()`, the check `serve` runs at startup, so the two cannot disagree; its findings also pass through a redactor that knows the secret. Under `verify: introspection` the key set is not checked, since nothing uses it, and the issuer's metadata only matters to MCP clients. An `introspection_endpoint` in the metadata that differs from the configured URL is a warning, not something `doctor` or `serve` follows: the URL stays configured (024). Each request has a deadline held by a timer (`withDeadline`) that covers the whole answer.
- **No allowed hosts setting.** apitame checks Host and Origin only on loopback, against DNS rebinding. Beyond loopback, where the image listens, authentication protects it and a page cannot attach a bearer token. For a proxy on the same machine forwarding to loopback, the host of `http.oauth.resource` is already accepted, and with the static token the proxy can send the upstream address as `Host`.

## 026. Paging list endpoints inside apitame

**Context.** Agents lose turns on list endpoints: they call once, read a cursor, a page number or a `next` link, and call again, often passing the cursor wrongly (the id of the first item instead of the last, a `next` URL as a parameter, a page number off by one). Each API pages differently, and a spec rarely says how in a machine-readable way (#63).

**Decision.** Detect a small set of styles from the spec when it loads, and let read tools fetch the following pages themselves.

- **Five styles, tried in a fixed order:** Stripe cursors (`starting_after` with `has_more`), a next token in the body paired with the parameter that takes it, next links (a declared `Link` header or a `next`-like field) with position parameters, `offset` with a page size, and `page` with a page size. Detection needs a response schema with a list, uses parameter names and types, and covers GET operations classified as reads only. An operation that matches nothing is not paged: a wrong guess would merge unrelated pages or loop, while missing paging only costs the agent a call. On the full public specs this finds 126 cursor and 7 token operations in Stripe's, and 194 next-link and 67 page-number operations in GitHub's. A page number without a page size is not enough, because nothing then says where the data ends. Without a declared `Link` header, GitHub's `before` and `after` cursors are left out rather than guessed.
- **`pages` is a control argument like `fields`.** It defaults to 1, is capped by `limits.maxPages` (default 5, at most 20) with a note rather than an error, and is offered only by tools with a paged operation. An API parameter called `pages` wins in single-operation tools, as `fields` does, because paging only shapes the result; `dryRun` and `confirm` keep their stricter rule because they decide whether something is sent. On a write, `pages` is refused before anything is sent. `limits.maxPages: 1` turns paging off entirely (no argument, no following requests, no `pagination`), so a server can opt out of the whole feature, not only of following pages.
- **Every paged result says how to continue.** `pagination` has `pages`, `more`, `next` (the exact arguments) and a `note` when paging stopped early, even with the default of one page: that is the part that saves agents the most mistakes. The cost is a few tokens per list result and about 150 tokens on the GitHub example's tool list (the `pages` property and one sentence in the server instructions).
- **A next link is never followed as it is.** Every following request is built from the same operation and validated arguments, with only the position parameters replaced, and the new position is validated against the schema. From a next link apitame takes only the position parameters the link sets, and only when the link stays on the API's origin and under the base path; every other argument stays as the agent gave it, except the other half of a cursor pair (`after` and `before`). Parameters with a `date` or `date-time` format are never positions: a first version took GitHub's `before` time filter on notifications for a cursor and dropped it on later pages. Link headers are parsed in one pass as RFC 8288 describes, quoted values included, so a `rel=next` inside a `title` cannot pose as a link and a hostile header costs linear time. Following the link would be simpler, but a response is untrusted: it could point at another host (with credentials attached), at another endpoint under the same host, or carry other filters. Rebuilding also handles GitHub, whose links point at `/repositories/{id}/...` rather than the path that was called. Links whose position lives in parameters the operation does not declare (Azure's `$skiptoken`, when the spec leaves it out) are therefore not followed. A refused link and an invalid position are recorded in the audit log as `refused`, and a refused link is logged as a warning at most once a minute per operation.
- **One budget for the whole call.** Pages are read one after the other, under the call's single `limits.timeoutMs` deadline, and each counts against the per-minute limits (server-wide, per tool and per caller), so `pages` cannot be used to get around them. A position the API already sent in the call stops paging. `limits.maxResponseBytes` covers `data` and `pagination` together, measured after field selection and redaction, never cutting an item. In the first version only `data` counted, and `next` came straight from the response: a 400 KB page token went back to the agent whole. Now a position longer than 2048 characters is not passed on at all, and the pages are fitted in a second step that measures each candidate cut with its own `pagination`. Item sizes are only measured as far as the budget could hold, and the cut is found by binary search, so a page of a million tiny items costs about as much as the budget, not the square of the page. Where a position can point inside a page (cursor and offset), the last page is cut between items and `next` continues after the last item returned; otherwise following pages are added whole or not at all, so `next` is always exact, and only a first page that is too large is cut with a note that `next` skips the rest. When paging stops at a limit or a failing page, the pages read so far are returned with `next`, instead of an error that would throw them away.
- **Not covered:** backward paging (Stripe's `ending_before` is given back in `next` but not followed), paging in request bodies, GraphQL-style `pageInfo`, and APIs that send links without declaring them. These can be added as styles when real specs need them.
